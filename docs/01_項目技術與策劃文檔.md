## 1. 項目概述 (Project Overview)

### 1.1 項目背景與痛點

* **旅遊體驗痛點**：澳門旅遊景區（如大三巴、官也街）空間緊湊，高峰期人流極度擁擠，嚴重影響遊覽體驗；同時，許多極具在地特色的老字號美食隱藏在街巷中，遊客常因資訊不對稱而錯過。
* **管理與技術痛點**：政府與景區管理者缺乏低成本、廣覆蓋的數據支撐來向公眾發佈實時人流預警。傳統依賴電信運營商基站數據的熱力圖成本高昂且屬於隱私數據，難以應用於面向公眾的輕量化小程序中。

### 1.2 核心目標

開發一款基於微信小程序的「澳行無阻」——澳門旅遊實時熱力圖與特色美食導覽系統，提供兩大核心價值：

1. **實時避峰參考（熱力圖）**：基於多源公開數據（官方 Open Data + 互聯網 API）構建人流估算模型，為遊客提供直觀的景區實時擁擠度熱力圖，輔助行程決策。
2. **在地美食發掘（POI 地圖）**：在地圖上精確標註澳門特色美食，打破資訊壁壘，引導遊客探索隱藏在周邊街巷的地道風味。

## 2. 系統功能架構 (System Architecture)

本項目採用前後端分離架構，重點實現地圖層次的疊加展示。

```
[微信小程序前端 (用戶交互層)]
    ├── 1. 實時景點熱力圖層（騰訊位置服務地圖組件 + Circle/Canvas 自繪熱力效果）
    ├── 2. 特色美食 POI 圖層 (地圖標註 + 多維篩選)
    └── 3. 地圖交互組件 (搜索、圖層切換、詳情卡片)

[後端數據與算法引擎 (邏輯層 - Python/Node.js)]
    ├── 澳門人流估算模型算法核心
    ├── 美食 POI 查詢與過濾接口
    └── 緩存與高並發處理層 (Redis)

[數據接入與持久化層 (數據庫與 API 層)]
    ├── 靜態數據庫：美食 POI 與景點基礎數據 (PostgreSQL/MySQL)
    └── 動態數據採集 (外部 API 接入)：
          ├── 澳門交通事務局 (DSAT) 開放數據（周邊停車場即時空位率，已確認有公開 API；巴士即時到站數據無法取得，不採用）
          ├── 澳門治安警察局 (PSP) （口岸通關人流，需確認公開可得性，見第 8 節）
          ├── 澳門地球物理暨氣象局 (SMG) 開放數據 API（實時天氣預警）
          └── 自有 macau_events_scraper（大型活動／演唱會排期，作為 H(t) 節假日放大係數的輸入源）
```

### 2.1 核心功能板塊詳情

#### 1. 實時景點熱力圖板塊 (Heatmap Layer)

* **動態可視化**：在全澳地圖上以直觀的色帶（綠色暢通-黃色緩行-紅色擁擠）展示重點景區的實時擁擠程度。
* **趨勢預測**：結合依地點類型分群的時段曲線，提供未來 1-2 小時的人流趨勢預判，幫助遊客提前規劃「何時前往」。
* **技術實作方案（本版新增）**：由於微信小程序原生 `<map>` 組件**不支援標準 Heatmap 圖層**，建議採用以下二選一方案：
  1. **Circle 疊加法（優先推薦，MVP 首選）**：以 `<map>` 組件內建的 `circles` 屬性，在各景點座標繪製半透明漸變色圓形，半徑與透明度依 CrowdIndex 動態調整，成本低、原生體驗佳，足以支撐競賽 Demo。
  2. **WebView 內嵌騰訊地圖 JS API**：若需要更精細的漣漪式熱力圖效果，可用 `<web-view>` 嵌入基於騰訊地圖 JavaScript API（內建 HeatmapLayer）的網頁，但需額外配置業務域名白名單，且與原生組件的手勢/性能體驗有落差，建議列為 Phase 2 優化項而非 MVP 必需。

#### 2. 在地特色美食地圖板塊 (Food POI Layer)

* **精準標註**：在熱力圖層之上（或切換至獨立圖層）疊加特色美食圖標（如「老字號」、「茶餐廳」、「米芝蓮小吃」）。
* **多維度篩選**：用戶可依據距離、菜系分類（葡國菜、粵菜、甜品）、人均消費等條件快速過濾地圖上的美食點。
* **詳情與導航**：點擊美食圖標彈出店鋪詳情卡片，展示招牌菜、營業時間、用戶評價，並支持一鍵拉起微信內置導航（`wx.openLocation`）。

## 3. 核心算法：人流估算模型 (Crowd Estimation Model)

為解決基站數據獲取難題，本項目採用**多源公開數據融合與加權擬合模型**來計算景區實時人流指數。

### 3.1 模型設計原則

在「無電信基站數據、僅能用免費公開 API」的限制下，必須誠實面對一個核心問題：**模型裡有沒有一個真正隨「此刻」變化的訊號，而不是全靠歷史規律預測？** 逐項檢視各因數的本質：

* $B(s)$（歷史基準熱度）、$T(t)$（時段曲線）、$H(t)$（假期/活動查表）本質上都是「已知規律」，不隨當天實況變化；
* $I(t)$（口岸通關量）、$W_{\text{weather}}(t)$（天氣）更新頻率較低，屬於慢變數；
* 唯一能承載「今天、此刻」真實變化的，是澳門交通事務局 (DSAT) 的**周邊停車場即時空位率**——已確認有公開 API，車位隨時間持續變化，是全模型裡貨真價實的即時訊號（原規劃並列的巴士即時到站數據，實際查證後無法取得，故不採用）。

因此 $P(s,t)$ 明確限定並改名為 $Park(s,t)$（停車場空位率），作為模型的即時訊號主力，而非與巴士數據混合的模糊「交通強度」。

此外，v1.1 版遺留兩個結構性問題一併修正：

* **時段曲線不應全澳共用一條**：廟宇廣場、商業步行街、室內場館、濱海景點的尖峰時段本來就不同（例如室內場館在雨天反而人潮上升），用一條萬用高斯曲線會系統性失準。改為依地點類型分群的 $T_c(s,t)$，將 50+ 重點區域歸入 4 類典型曲線（廟宇廣場型／商業步行街型／室內場館型／濱海戶外型），不需要為每個地點單獨建模，工作量可控。
* **天氣係數方向需依室內外翻轉**：下雨天室外廣場人潮下降，室內場館（博物館、賭場、商場）人潮通常反而上升（遊客避雨）。原本全澳用同一個 $W_{\text{weather}}(t)$，對室內景點方向是錯的。改為 $W(s,t)$，依地點的室內/室外標記翻轉修正方向。

修正後模型如下：

$$\text{CrowdIndex}(s, t) = \underbrace{\left[ w_1 \cdot B(s) \cdot T_c(s, t) + w_2 \cdot Park(s, t) \right]}_{\text{基礎人流信號（加權求和，} w_1+w_2=1\text{）}} \times \underbrace{I(t) \times W(s, t) \times H(t)}_{\text{宏觀修正係數（連乘）}}$$

| 影響因數 | 符號 | 數據量化方式 | 獲取來源 (Data Sources) |
| --- | --- | --- | --- |
| **景點基準熱度** | $B(s)$ | 歸一化值 $[0, 1]$ | 澳門旅遊局歷史訪客統計、地圖 POI 搜索熱度（實作時以騰訊位置服務 POI 熱力/簽到數據為準，而非高德）。 |
| **分群時段曲線** | $T_c(s, t)$ | 高斯擬合曲線 $[0, 1.2]$，依地點類型 $c$ 分 4 群 | 基於澳門歷史客流規律構建，各群峰值時段不同（如商業步行街 14:00–16:00、濱海景點 17:00–19:00）。 |
| **周邊停車場即時空位率** | $Park(s, t)$ | 歸一化值 $[0, 1]$（空位率越低，代表車流/人流越旺） | **澳門交通事務局 (DSAT)** 開放數據 API，已確認可用，是模型唯一的即時訊號（巴士即時到站數據無法取得，不採用）。 |
| **全澳總客流權重** | $I(t)$ | 乘法係數 $[0.8, 1.3]$ | **澳門治安警察局**（關閘、港珠澳大橋等主要口岸實時通關人流量；可得性待確認，見第 8 節）。全澳單一數值，不分地點，屬於粗粒度宏觀修正。 |
| **天氣修正係數（依室內外翻轉）** | $W(s, t)$ | 乘法係數，室外 $[0.2, 1.1]$／室內 $[1.0, 1.3]$ | **澳門地球物理暨氣象局 (SMG)** 開放數據 API；每個地點預先標記室內/室外，暴雨/颱風下室外係數降低、室內係數上升。 |
| **節假日/活動放大係數** | $H(t)$ | 乘法係數 $[1.0, 2.0]$ | 內地及澳門官方公眾假期日曆；**大型演唱會/活動期間額外放大，可直接串接自有 `macau_events_scraper` 抓取的活動排期作為真實輸入**。 |

> **模型說明**：通過調節權重（如 $w_1 = 0.6$, $w_2 = 0.4$），算法能夠在缺乏絕對真實人數的情況下，輸出相對的「擁擠程度」，且透過 $Park(s,t)$ 保有真正的即時變動，而非純日曆式預測。計算完成後，建議在同一時間切片 $t$ 下對全澳 50+ 重點區域的 CrowdIndex 做 **Min-Max 正規化**，再映射至三段色帶（綠/黃/紅），確保熱力圖呈現的是「相對擁擠排名」而非絕對數值，避免因基準值差異導致色帶失真。

### 3.2 已知限制與後續優化方向

* **$Park(s,t)$ 對步行區的代表性有限**：大三巴、議事亭前地等核心景點是步行區，停車場空位率反映的是「開車/搭車進入這一帶的人」，跟廣場實際人流有相關性但非直接等價，且會有 10–20 分鐘左右的滯後（停車到步行抵達的時間差）。目前以此作為 MVP 階段最務實可得的即時代理指標，答辯時應誠實說明這個侷限，而非包裝成精確的人數統計。
* **$I(t)$ 是全澳單一數值，非逐點精確**：口岸通關量暴增時，遊客不會瞬時均勻擴散到每個景點，會先湧向知名地標。目前簡化為全澳統一乘數，是可接受的 MVP 簡化，但非逐點精確。
* **Phase 2 路線圖：加入用戶自報訊號 $U(s,t)$**：待累積真實用戶後，於前端加入「現在人多嗎？」一鍵回報功能（概念上與 Waze 的路況回報、Google 地圖「常去時段」相同），作為真正由用戶產生的即時修正項。MVP 階段不做（無用戶基數，回報數據不具意義），此處僅記錄為明確的下一步方向，不寫入現行公式。

## 4. UI/UX 與交互設計方案 (User Experience Design)

小程序的交互設計強調「地圖即服務（Map as a Service）」，減少頁面跳轉：

1. **首頁地圖視圖 (Map View)**
   * **主界面**：打開即顯示帶有實時熱力圖的澳門地圖。
   * **圖層控制 (Layer Control)**：右側設置醒目的懸浮按鈕，允許用戶自由切換視圖：**「純熱力圖」**、**「純美食地圖」** 或 **「熱力+美食疊加圖」**。

2. **快捷搜索與篩選 (Search & Filter)**
   * 頂部為懸浮搜索框，支持景區與美食的模糊搜索。搜索框下方設有橫向滑動的快捷篩選標籤（如「附近葡國菜」、「人少景點」）。

3. **信息抽屜 (Bottom Drawer)**
   * 點擊地圖上的景區或美食圖標後，從底部彈出半屏抽屜式詳情卡片（包含擁擠度趨勢圖、或餐廳招牌菜及導航按鈕），用戶下滑即可收起，視線始終不離開地圖。

## 5. 數據更新與性能優化 (Data Flow & Performance)

由於地圖類小程序對響應速度要求極高，系統後端設計如下：

1. **定時異步採集**：後端服務（Python）設置 Cron Job，每 5-10 分鐘在後台調用一次 DSAT、SMG 等外部 API 獲取最新變量；`macau_events_scraper` 可獨立以較長週期（如每日）執行，更新活動排期表供 $H(t)$ 查詢。
2. **模型計算與預處理**：後台依據最新變量，計算出全澳 50+ 重點區域的最新 $\text{CrowdIndex}$，正規化後格式化為前端所需的地圖組件數據格式（Circle 座標、半徑、顏色）。
3. **Redis 高速緩存（性能關鍵）**：將計算完成的熱力數組寫入 Redis 緩存。當大量遊客同時打開小程序時，API 請求直接命中 Redis 返回數據，實現地圖渲染的秒級響應，避免大量併發壓垮數據庫。

### 5.1 數據源不可得時的備援方案

若某一政府 API 在開發期間暫時無法申請取得（詳見第 8 節風險列表），對應變量以下列方式退化，確保系統仍可運作與展示：

* $Park(s,t)$（停車場空位率）：若 API 臨時異常，以歷史同時段平均值 + $T_c(s,t)$ 曲線估算，不阻斷整體模型輸出。
* $I(t)$（口岸客流）：預設為 1.0（不放大不縮小），待取得數據後再啟用。
* $H(t)$：優先使用 `macau_events_scraper` 產出的活動數據作為可控、穩定的替代信號。

## 6. 未來拓展方向：AI 旅遊助手 (Future Work)

在系統積累了一定的使用數據與完善 POI 庫後，項目計畫在未來版本（Phase 2）引入基於大語言模型（LLM）的智能交互功能，進一步提升智慧旅遊體驗：

* **自然語言查詢**：用戶不再需要手動點擊篩選標籤，可直接透過語音或文字詢問，例如：「現在大三巴人多嗎？附近有沒有不用排隊的老字號糖水鋪？」
* **AI 行程動態重構**：結合用戶的實時位置、當前各大景區的熱力擁擠度以及天氣狀況，AI Agent 可以自動生成或實時動態調整旅遊路線，實現真正意義上的「智慧避峰導覽」。

## 7. 項目亮點與評委答辯優勢 (Key Highlights for Competition)

1. **技術落地性強，開發成本低**：摒棄昂貴的運營商私有數據，完全利用公開 API 與自研數學估算模型實現熱力圖功能，具備極高的性價比，可快速構建原型（MVP）並投入實際演示。
2. **切中政策方向**：項目高度契合澳門特區政府推動「智慧城市」、「智慧旅遊」與「旅客分流」的戰略方針。
3. **活化社區經濟**：通過清晰標註隱藏在街巷中的特色美食，引導遊客離開過度擁擠的核心景區，深入社區探索，為非核心區的小微餐飲店家帶來實際的商業引流。
4. **風險意識完整**：對政府數據源的可得性做了逐項評估並設計備援方案（見第 8 節），展現團隊工程成熟度，而非僅停留在理想化假設。
