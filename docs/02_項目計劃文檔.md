## 1. 項目目標與範圍界定 (Goals & Scope)

### 1.1 比賽 MVP 目標

在競賽演示前，交付一個可實機操作的微信小程序 Demo，須包含：

1. 澳門地圖上，至少 10-15 個重點景區的「模擬/真實」CrowdIndex 熱力顯示（三色帶）。
2. 至少 30-50 筆特色美食 POI，具備分類篩選與詳情卡片。
3. 熱力圖 + 美食圖層可自由切換與疊加。
4. 後端具備基本的定時計算與 Redis 緩存架構（即使部分政府數據暫以模擬值代替）。

### 1.2 明確不做（Out of Scope，避免比賽前範圍蔓延）

* AI 旅遊助手（自然語言查詢 / 行程動態重構）— 列為 Future Work，比賽階段僅需在文檔與 Pitch 中說明構想，不需要實作。
* 熱力圖與美食的「聯動推薦算法」— 依先前決策已剔除，兩圖層各自獨立疊加展示即可。
* 用戶帳號系統、訂單/支付功能 — 非本次核心價值主張，不做。

## 3. 開發時程與里程碑 (Timeline & Milestones)

比賽截止日期尚未在對話中提供，以下以**相對週數**規劃，請對照實際比賽日期換算為具體日曆日並回填。

| 階段 | 週次 | 核心產出 | 驗收標準 |
| --- | --- | --- | --- |
| **Phase 0：準備與確認** | Week 1 | 完成本文檔與技術文檔評審；完成 DSAT/SMG/PSP 開放數據申請與條款確認；美食 POI 清單初稿（Excel/CSV） | 至少 1 個政府 API 拿到可用 Key 或確認無法取得並定案備援方案 |
| **Phase 1：後端骨架** | Week 2 | 資料庫 Schema（景點、POI）、CrowdIndex 模型程式碼（可用模擬數據跑通）、Redis 緩存串接 | 本地可用假數據算出 50 個地點的正規化 CrowdIndex |
| **Phase 2：前端骨架** | Week 2-3 | 小程序項目初始化、地圖組件接入騰訊位置服務、基本頁面路由與抽屜 UI | 地圖可正常顯示、可點擊標記彈出詳情卡片（假數據） |
| **Phase 3：熱力圖層整合** | Week 3-4 | 前後端串接，Circle 疊加熱力效果、三色帶邏輯、趨勢預測（時間衰減曲線） | 熱力圖隨後端數據更新即時刷新，色帶符合擁擠度直覺 |
| **Phase 4：美食圖層整合** | Week 4-5 | POI 篩選（距離/菜系/價位）、搜索框、一鍵導航 | 篩選結果與地圖標註同步，導航可正確拉起微信內置地圖 |
| **Phase 5：串接真實數據源** | Week 5-6 | 接入已核准的政府 API；`macau_events_scraper` 排程串接作為 $H(t)$ 輸入 | 至少 1-2 個真實數據源已取代模擬數據 |
| **Phase 6：性能與穩定性** | Week 6 | Cron Job 排程穩定性測試、Redis 緩存命中率驗證、併發壓力測試（模擬多人同開） | 熱力圖 API 響應 < 500ms（命中緩存情境） |
| **Phase 7：Demo 打磨與答辯準備** | Week 7 | UI 細節打磨、Pitch 簡報、Demo 腳本演練、常見問答準備（尤其第 8 節風險項） | 完整走一遍 Demo 流程無卡頓/崩潰 |
| **Phase 8：比賽提交** | Week 8 | 提交材料整理（代碼、簡報、Demo 影片）、README 更新 | 依比賽方要求的截止時間前完成提交 |

## 4. 技術棧與工具清單 (Tech Stack Checklist)

| 類別 | 選型 | 備註 |
| --- | --- | --- |
| 小程序框架 | 微信原生小程序 / 或 Taro（可選） | 若團隊熟悉 React，Taro 可加速開發，但需確認地圖組件相容性 |

| 緩存 | Redis | 存放計算後的 CrowdIndex 結果 |
| 排程 | Cron Job / APScheduler | 5-10 分鐘週期拉取外部 API |
| 版本控制 | GitHub（本 repo） | 已具備，建議建立 `feature/*` 分支規範 |
| 專案管理 | Trello / Notion / GitHub Projects（擇一） | 用於追蹤 Phase 0-8 任務進度 |

## 7. 測試與驗收計劃 (Testing & Acceptance)

1. **功能測試**：地圖載入、圖層切換、篩選、詳情抽屜、導航跳轉，逐項手動測試通過。
2. **數據正確性測試**：抽查 5-10 個景點的 CrowdIndex 計算結果，人工核對公式各項輸入是否符合預期。
3. **性能測試**：模擬多次連續請求，確認 Redis 緩存命中後響應時間 < 500ms。
4. **Demo 彩排**：Phase 7 至少完整彩排 2 次，包含應對評委追問（尤其數據來源真實性、AI 助手為何列為 Future Work）。

## 8. 比賽提交與展示規劃 (Submission & Demo Plan)

* **Pitch 敘事主軸**：「左手看擁擠（熱力圖），右手看好吃（美食圖），決定權交給遊客」— 呼應技術文檔中已定案的核心邏輯，避免展示時偏離主軸去講 AI 助手等 Future Work。
* **建議 Demo 流程**：
  1. 打開小程序 → 展示疊加圖層首頁
  2. 點擊熱力圖高擁擠景點 → 展示趨勢預測
  3. 切換至美食圖層 → 篩選「附近葡國菜」→ 點擊詳情 → 導航
  4. 收尾：簡述數據來源與風險應對（展現工程成熟度）、展望 AI 助手 Future Work
* **提交材料清單**：代碼倉庫（本 repo）、簡報（含系統架構圖、模型公式、UI 截圖）、Demo 錄影（防現場網路/API 故障）、README 更新（分工、安裝與執行方式）。
